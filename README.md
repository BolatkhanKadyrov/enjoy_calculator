# Цех — сервис расчёта себестоимости

Текущая версия кода: **0.9.0 — роли и завершение сеансов**. Владелец имеет все права и назначает администраторов. Администратор получает все рабочие права и управляет обычными сотрудниками; полные копии и восстановление остаются у владельца. Во вкладке «Сотрудники» можно завершить все входы выбранного аккаунта без смены его пароля. Проверки выполняются на сервере, включая ранее открытые формы. Подробности и статус выпуска — [роли и сеансы](docs/roles-and-sessions.md).

Рабочий путь: вход → сырьё и упаковка → заготовки → блюдо → предварительный расчёт → сохранение → повторное открытие. Поставщик необязателен. Доступны вложенные заготовки, пересчёт зависимостей, изменение выхода, первичные потери, точные количества и журнал. Скидка применяется только для анализа; общие и индивидуальные пороги определяют зоны и минимальную отпускную цену.

Управление ценами, таблица и график истории доступны через «Цены и история» в карточке сырья/упаковки. Закупки, доставка и средневзвешенные цены доступны в разделе «Закупки и доставка». ## Репозиторий и непрерывная проверка

Исходники: [BolatkhanKadyrov/enjoy_calculator](https://github.com/BolatkhanKadyrov/enjoy_calculator). Репозиторий публичный; локальные данные, `.env`, ключи, копии БД и браузерный профиль исключены. Пароли в тестах/CI предназначены только для одноразовой тестовой PostgreSQL, их нельзя использовать в рабочем окружении.

[GitHub Actions](https://github.com/BolatkhanKadyrov/enjoy_calculator/actions) запускает полный Python/PostgreSQL-набор и пять JavaScript-наборов, а также собирает Docker и проверяет настоящий Linux Gunicorn: чистую схему, UID 10001, PORT, HTTPS-заголовки, health, static и maintenance. Запуск возможен по push в `main`, pull request или вручную. Workflow не публикует образ и не развёртывает Railway. Подтверждённый успешный прогон и границы проверки описаны в [отчёте CI](docs/github-verification.md); для последующих изменений результат нужно смотреть у соответствующего коммита.

На машине с Docker контейнерную проверку можно повторить командами `docker build -t tseh-ci:smoke .` и `bash scripts/ci-smoke.sh tseh-ci:smoke`. Скрипт создаёт собственную временную PostgreSQL, не использует рабочий `DATABASE_URL` и удаляет только созданные им контейнеры/сеть.

## Требования

- Python 3.14; точные Python-зависимости — `requirements.lock`.
- PostgreSQL 17. Транзакционные тесты требуют реальную PostgreSQL, SQLite не поддерживается.
- Первый владелец создаётся вручную командой `create_owner`; он назначает администраторов, а владелец и администраторы добавляют сотрудников в интерфейсе. Вшитого пароля, автоматических пользователей и демоданных нет.

## Локальный запуск на этом Windows-компьютере

Подготовленные `.venv` и `.local` игнорируются системой контроля версий. PostgreSQL из проверенного EDB ZIP распакована в `.local/postgresql/pgsql`; кластер `.local/pgdata` слушает только `127.0.0.1:55432`, системная служба не создаётся. Случайные локальные секреты в `.local/dev.json`; не публиковать этот файл.

```powershell
.venv\Scripts\python.exe scripts\dev.py start-db
.venv\Scripts\python.exe scripts\dev.py manage migrate
.venv\Scripts\python.exe scripts\dev.py manage create_owner
.venv\Scripts\python.exe scripts\dev.py manage runserver 127.0.0.1:8000 --noreload
```

Открыть http://127.0.0.1:8000/. Команда `create_owner` создаёт первого владельца с логином `tseh`; другой логин можно задать через `--username ИМЯ`. Пароль вводится дважды интерактивно, без отображения; минимум 12 символов и проверка сложности. Команда не меняет существующие аккаунты и отказывается создавать второго владельца. Публичной регистрации и Django admin нет. Обычный `createsuperuser` не выдаёт права в приложении: они определяются профилем доступа. Сменить пароль владельца: `scripts\dev.py manage changepassword ИМЯ`; управляемым аккаунтам — через вкладку «Сотрудники».

При обновлении существующей версии миграция `0013_employee_access` добавляет профиль владельца активным аккаунтам `tseh` и `tseh_staging`, сохраняя их пароли. Повторный `create_owner` для них не нужен. Учётные записи с другими логинами автоматически прав не получают. Миграция `0015_staff_roles_and_sessions` добавляет отдельную роль администратора и завершение сеансов; существующие сотрудники не повышаются в правах автоматически.

Остановка сервера: Ctrl+C. Остановка принадлежащего проекту PostgreSQL:

```powershell
.venv\Scripts\python.exe scripts\dev.py stop-db
```

`start-db` создаёт пустые базы `tseh` и отдельную `tseh_qa` для интерфейсной проверки; данные в рабочую базу не добавляет. Локальный владелец кластера нужен для создания тестовой БД. В Railway production приложение использует отдельную роль с необходимыми правами, не администратора кластера.

## Обновление уже используемой локальной версии

```powershell
.\scripts\serve.ps1 -Upgrade
```

Скрипт проверяет принадлежность сервера на `127.0.0.1:8000` этому проекту и останавливает его. Затем создаёт архив PostgreSQL в `.local/backups`, пробно восстанавливает его в отдельную временную БД, удаляет только эту проверочную БД, применяет миграции и запускает приложение скрытым процессом. Ошибка копирования, восстановления или миграции прерывает обновление. Существующие учётная запись, цены и рецептуры сохраняются; открытые до обновления формы нужно открыть заново.

`scripts/upgrade_local.py` — внутренняя часть процедуры; для рабочей локальной базы используйте `serve.ps1 -Upgrade`, чтобы на время копирования остановить также авторизацию и записи сессий. Копия содержит данные и учётные записи: не публикуйте её. Она остаётся локальной и не защищает от потери компьютера.

Запуск без миграций: `.\scripts\serve.ps1`. Остановка только приложения: `.\scripts\serve.ps1 -Stop`. Логи: `.local/web.log` и `.local/web-error.log`. PostgreSQL останавливается отдельной командой `scripts/dev.py stop-db` после остановки приложения.

```powershell
uv venv --python 3.14 .venv
uv pip install --python .venv\Scripts\python.exe -r requirements.lock
```

Предоставьте PostgreSQL и задайте переменные из `.env.example` в окружении процесса. Файл `.env` автоматически не загружается. `DATABASE_URL` обязателен, секрет должен быть случайным (от 32 символов для локального DEBUG, от 50 для production). При локальном HTTP задайте `DJANGO_DEBUG=1` и `DJANGO_SECURE_SSL_REDIRECT=0`. Затем `python manage.py migrate`, `python manage.py create_owner`, `python manage.py runserver`. Для production используйте Docker/Gunicorn и отдельную команду миграций по [инструкции](docs/railway.md); DEBUG выключен, обязательны явные hosts, HTTPS и безопасные cookies. Прокси-заголовки по умолчанию не считаются доверенными.

## Проверка первого сценария

1. При необходимости добавить поставщика; этот шаг можно пропустить.
2. Создать ингредиент «Курица», кг, потери 25%, упаковка 5 кг за 10000 ₸.
3. Создать блюдо: 100 г курицы и отпускная цена 700 ₸.
4. Нажать «Рассчитать себестоимость»: ожидается **~266,67 ₸**. На этом шаге блюдо ещё не сохраняется.
5. Сохранить и повторно открыть: количество и результат не меняются.
6. Изменить рецепт на 80 г: сравнение показывает 213,33 ₸. Отмена сохраняет прежнюю рецептуру.
7. Открыть одну форму в двух вкладках: после сохранения первой вторая должна отклонить устаревшую запись.
8. В журнале проверить создание, применение первой цены и сохранение блюда.

Запятая и точка принимаются для дробных значений. `~` обозначает округление для отображения. Промежуточные стоимости не обрезаются до сотых; итог округляется после сложения. Потери при готовке дополнительно не применяются. Нулевая закупочная цена требует явной отметки.

## Приёмка второго этапа

Это небольшой набор проверок для новой версии. Используйте отдельные тестовые позиции, чтобы не менять уже введённые рецептуры.

1. Создайте сырьё без потерь: фасовка 1 кг, цена 3000 ₸. Создайте заготовку из 1 кг этого сырья с выходом **2 кг**. Стоимость единицы — **1500 ₸/кг**. Блюдо из 100 г заготовки — **150 ₸**.
2. У заготовки измените выход на **1,5 кг**. До подтверждения сравнение должно показывать стоимость блюда **150 → 200 ₸**. После сохранения новое значение остаётся при повторном открытии; отмена сохраняет старое.
3. При редактировании выхода **2 кг** переключите единицу на г: количество становится **2000 г**, стоимость не меняется. То же преобразование работает в строках рецептур. Вложенная заготовка должна пересчитываться вместе с зависящим от неё блюдом; цикл сохраниться не должен.
4. Добавьте позицию типа «Упаковка»: 500 шт. за 25000 ₸. Одна штука добавляет к блюду **50 ₸**. Упаковка не допускает первичных потерь и не включается в заготовки.
5. Для отдельного блюда с себестоимостью **120 ₸** задайте отпускную цену **333,33 ₸**, общие пороги **40% / 60%**, скидку анализа **10%**. Ожидаются эффективная цена **300,00 ₸**, доля **40%**, зелёная зона и минимальная цена **333,33 ₸**. Скидка не меняет сохранённую отпускную цену и не создаёт запись журнала.
6. При общих порогах **40 / 60** задайте другому блюду свой зелёный порог **55** и общий оранжевый. Затем поменяйте общий оранжевый на **50**: изменение сохраняется, у блюда виден конфликт без цвета и без минимальной цены, C и r остаются. Возврат зелёного порога блюда к общему значению устраняет конфликт. Прямой ввод пары **60 / 50** отклоняется.

Проверьте также, что прежние рецептуры открываются, а новые подтверждённые изменения видны в журнале. Общие пороги изначально не назначаются автоматически.

Уточнения интерфейса: компонент убирается кнопкой «Удалить компонент»; действие не удаляет его из справочника и не сохраняет рецептуру до подтверждения. Поставщик при добавлении сырья/упаковки необязателен. Критерии UX/UI и правила независимого ревью для следующих этапов — в [docs/ux-ui-acceptance.md](docs/ux-ui-acceptance.md).

В редакторе компонент можно найти по части названия; группы сырья, упаковки и заготовок сохранены. Единица подбирается автоматически. Черновик рецептуры сохраняется в текущей вкладке при обновлении; «Обновить данные» и «Сбросить черновик» разделены. В списках блюд, сырья, заготовок, поставщиков и журнала доступны поиск, уместные фильтры, сортировка и страницы по 30 результатов. Спецификация и результаты проверки — в [docs/design-editor.md](docs/design-editor.md); распределение ответственности команды — в [docs/team-workflow.md](docs/team-workflow.md).

## Приёмка третьего этапа

Сохранение предложения не меняет действующую цену. Применение, исправление и удаление проходят отдельный предпросмотр; действующая цена удаляется только с заменой. История показывает все применения по времени, включая возврат к прежней цене. Комментарии, разовая отметка и исходные значения после исправления/удаления доступны в журнале.

Проверки, ограничения и короткий сценарий: [docs/stage-3-verification.md](docs/stage-3-verification.md). На этом этапе история показывает цену товара; доставка подключается на этапе 4.

## Сохранность и ограничения текущего этапа

Доменные изменения проходят через транзакционные команды вместе с журналом. Одна общая ревизия намеренно консервативна: даже несвязанная правка иногда требует обновить форму. Несколько входов разрешены. Новые записи журнала сохраняют логин выполнившего действие аккаунта; старым записям автор не назначается задним числом.

С 09.11.2026 согласованы три роли. Владелец `tseh` имеет все права и назначает администраторов. Администратор автоматически получает все рабочие права, включая общие пороги, и управляет обычными сотрудниками; владельца, себя и других администраторов он не меняет. Сотруднику назначаются просмотр, добавление, изменение и удаление по разделам: блюда, заготовки, сырьё/упаковка, цены, закупки и поставщики; журнал имеет право просмотра. Связанные разрешения, нужные для операции, добавляются по правилам формы. При понижении администратора до сотрудника остаются только явно выбранные права. Полные JSON/XLSX и восстановление доступны исключительно владельцу.

Отключение аккаунта завершает его входы, запрещает новые и сохраняет данные и историю. Смена логина, пароля, роли или прав также завершает входы изменённого аккаунта. Отдельное действие «Завершить сеансы» для активного управляемого аккаунта сохраняет пароль и возможность войти снова. Владелец может завершить и все собственные сеансы, включая текущий; администратор не выполняет это действие над собой или другим администратором. Прежний логин резервируется за тем же аккаунтом и не может быть выдан другому. Состояние выпуска и подробные границы — в [docs/roles-and-sessions.md](docs/roles-and-sessions.md); история версии 0.8.0 — в [docs/staff-access.md](docs/staff-access.md).

Пользовательские JSON-резервирование и восстановление реализованы и проверены на отдельной QA-базе. JSON не включает учётные записи и сессии; полный `pg_dump` PostgreSQL нужен дополнительно перед миграциями. Роли PostgreSQL и секреты восстанавливаются отдельно. Процедуры и ограничения приведены в [инструкции эксплуатации](docs/railway.md). Не удаляйте `.local/pgdata` при работающей базе.

Railway production запущен с пустыми доменными данными по выбору заказчика; staging сохраняет отдельные тестовые данные. Это не перенос локальной базы и не завершённая приёмка реальных рецептур. Актуальные результаты — в [отчёте production](docs/railway-production-verification.md). Миграции не запускаются при импорте приложения или обычном старте web. `/health/` раскрывает только доступность БД, не доменные данные. Автоматические копии остаются в бэклоге за пределами v1: регулярно скачивайте JSON и храните отдельно от контейнера и единственного компьютера.

Ограничение входа по умолчанию — 10 попыток за фиксированные 5 минут на источник. Успешный вход не обнуляет прежние ошибки; блокировка не продлевается новыми запросами. Действующие сессии продолжают работать. Устройства за одним NAT могут делить временную квоту; общей блокировки учётной записи нет. PostgreSQL хранит HMAC источника и счётчик, не исходный IP/логин/пароль. `DJANGO_LOGIN_MAX_ATTEMPTS` допускает 1–1000, `DJANGO_LOGIN_WINDOW_SECONDS` — 1–86400 секунд. Это ограничение перебора, не защита от распределённой атаки.


## Архив и общая корзина

В карточке блюда: «Убрать в архив» → «В корзину». Восстановление из корзины возвращает блюдо в архив; «Вернуть в ассортимент» — отдельное действие. Архив хранится бессрочно. Для блюда в корзине срок — 30 дней от помещения, окончательное удаление происходит на очередном запуске очистки, а не точно в секунду истечения срока.

По уточнению заказчика сырьё/упаковка, заготовки и поставщики также имеют корзину. Они хранятся в ней **бессрочно**, восстанавливаются в справочник и удаляются только отдельным подтверждённым действием. Связанные записи нельзя переместить в корзину; экран показывает рецептуры (включая архив/корзину), закупки и цены, мешающие переносу. Собственные цены и применения сырья сохраняются вместе с ним в корзине, а при явном окончательном удалении удаляются вместе с позицией; полный снимок остаётся в журнале. Справочники в корзине недоступны для выбора в новых формах.

«Архив и корзина» содержит поиск по названию, фильтр по типу записи и сортировку по названию/времени перемещения. Уникальность блюда определяется относительно других **активных** блюд; архив и корзина не снижают её. В карточке неактивного блюда сравнение также производится с активным ассортиментом.

## Ручные копии, восстановление и Excel

Только владельцу доступен раздел «Копии и экспорт»: регулярно скачивайте полную JSON-копию и храните её отдельно от компьютера. Автоматическая отправка и резервирование не настроены. JSON сохраняет доменные данные, точные исходные значения, последовательность применений цен, журнал с авторами и состояния корзины; версия формата — 1. Старые копии без авторов журнала принимаются, автор остаётся неизвестным. Пароли, пользователи, роли, права, история управления сотрудниками, секреты, сессии, технические квитанции команд и подготовки восстановления не экспортируются. Импорт сохраняет текущие аккаунты и их права.

Восстановление **заменяет**, а не объединяет данные и журнал:

1. Загрузить JSON и проверить показанный состав.
2. Скачать предоставленную JSON-копию текущего состояния. Сервис не определяет папку загрузок и не может подтвердить фактическое сохранение файла за пользователя.
3. Отметить подтверждение скачивания и замены, нажать «Заменить данные из файла».

Если данные изменились после подготовки копии, сформируйте и скачайте свежую копию, затем подтвердите заново. Подтверждение связано с конкретной версией копии: старую форму из другой вкладки применить нельзя. Замена атомарна, повторное подтверждение не дублирует импорт; все старые доменные формы инвалидируются новым поколением данных. Импортированный журнал сохраняется, добавляется событие восстановления. Журнал, заменённый импортом, остаётся в скачанной предимпортной копии.

Для блюд в корзине JSON хранит точный остаток срока в микросекундах. После восстановления отсчёт начинается с этого остатка: 12 дней остаются 12 днями, нулевой остаток не получает новый срок. Исторические даты сохраняются; новый срок отражается в журнале. Бессрочная корзина справочников восстанавливается бессрочно.

Технические пределы JSON: 25 МиБ, 50 000 доменных записей, вложенность структуры до 32 уровней. Неизвестная версия, дубли ключей, неверные типы/ссылки/единицы/циклы/снимки отклоняются целиком. Экспорт сам проверяет восстанавливаемость; он не обрезает журнал при достижении предела. Подготовленный импорт и предимпортная копия временно хранятся в PostgreSQL, доступны владельцу входа до 24 часов. Это не постоянный автоматический бэкап: сохраните скачанный файл у себя.

XLSX — статический отчёт на 12 листах с текущей скидкой анализа, датой, валютой и единицами. Включает все состояния, рецептуры, заготовки, позиции, цены и применения, поставщиков, закупки и доставку. Числа ограничены возможностями Excel, длинные идентификаторы и пользовательский текст записываются текстом и не исполняются как формулы. Для точного переноса используйте JSON. Импорта Excel нет.

## Команды ежедневного обслуживания

В Railway production и staging настроены отдельные maintenance-сервисы с расписанием `0 2 * * *`: ежедневно в 02:00 UTC, то есть 07:00 Asia/Qyzylorda. В staging подтверждены автоматические запуски 6 и 7 ноября; в production 7 ноября подтверждён ручной запуск `EXITED`, первый автоматический ожидается 8 ноября. Для другого окружения расписание нужно создать отдельно. В окружении приложения с обычными переменными БД доступны команды:

```text
python manage.py purge_trash
python manage.py purge_restore_sessions
```

`purge_trash` удаляет только просроченные **блюда**, сохраняет журнал и безопасен при повторном/конкурирующем запуске. Бессрочную корзину справочников команда не затрагивает. `purge_restore_sessions` удаляет истёкшие временные подготовки восстановления; доменные данные и журнал не меняет. Если очистка не запускается, просроченные записи остаются до следующего запуска. Команда `sh scripts/start-production.sh maintenance` также очищает старые счётчики входа и истёкшие сессии, но не создаёт резервных копий. Настройки ежедневного запуска описаны в [инструкции Railway](docs/railway.md), фактические запуски — в [отчёте production](docs/railway-production-verification.md).

Локально команды вызываются через `.venv\Scripts\python.exe scripts\dev.py manage ИМЯ_КОМАНДЫ`. Для QA используйте `qa` вместо `manage`. Не запускайте очистку рабочей БД ради проверки — тесты используют отдельную БД.
