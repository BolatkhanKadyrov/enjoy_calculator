# UX/UI — критерии и порядок проверки

Редакция 2 от 04.11.2026. Основание: просьбы заказчика заменить чекбокс удаления кнопкой, разрешить сырьё без поставщика, сохранять работу при F5/обновлении и ввести независимую проверку UX/UI. Это рабочие критерии качества интерфейса; расчётные правила остаются в исходных требованиях и `decisions.md`.

## Проверяемые критерии

| ID | Критерий | Проверка и ожидаемый результат |
| --- | --- | --- |
| UX-01 | Явное удаление компонента | В новом и существующем блюде/заготовке есть кнопка «Удалить компонент». Она убирает выбранную строку, включая пустую или ошибочную; позиции справочника остаются. До сохранения и при отмене исходная рецептура не меняется. |
| UX-02 | Состав и пределы | После удаления последней строки понятно, что нужен хотя бы один компонент. Введённые название/выход/цена остаются. При 100 компонентах предел объяснён; удаление позволяет добавить замену. |
| UX-03 | Необязательный поставщик | Можно создать первую позицию сырья без единого поставщика в базе. Поле подписано «необязательно»; в карточке/списке отсутствие показано как «Не указан». Фасовка, цена и дата по-прежнему проверяются; фиктивного поставщика нет. |
| UX-04 | Понятное подтверждение | Расчёт и сохранение разделены. Предпросмотр явно говорит, что изменения не сохранены. После изменения состава/параметров старый расчёт помечен устаревшим, сохранение требует пересчёта. Подмена старого подтверждения отвергается сервером. |
| UX-05 | Исправимые ошибки | Ошибки объясняют, что исправить, находятся у поля или в общей сводке, не стирают остальные значения. После отправки фокус переходит к ошибке либо новому расчёту. Устаревшая форма не перезаписывает более свежие данные. |
| UX-06 | Точные и понятные величины | У чисел видны единицы и смысл: закупочная фасовка, чистое количество, готовый выход, порция. Запятая и точка принимаются; г↔кг и мл↔л не меняют физического количества. Отображение округления не меняет расчёт. |
| UX-07 | Работа при обновлении | В редакторах блюда/заготовки F5 и отдельная кнопка «Обновить данные» сохраняют введённый черновик при доступных JS/sessionStorage. После восстановления нужен новый расчёт. Черновик не смешивается между аккаунтами/формами; изменённая база обозначена предупреждением. Подробные проверки — ED-08–09. |
| UX-08 | Явная очистка и отказ хранилища | «Сбросить черновик» требует подтверждения. Успешное сохранение очищает только соответствующую копию; ошибка/submit не очищают её. Недоступное хранилище объяснено, кнопка обновления при неудачной записи не выполняет переход. Не обещается восстановление после закрытия вкладки или без JS. Подробные проверки — ED-10–12. |
| UI-01 | Клавиатура | Сценарий можно пройти Tab/Shift+Tab и Enter/Space. Enter в обычном поле запускает расчёт и не удаляет компонент; удаление происходит только при явной активации его кнопки. Фокус виден. У удаления есть имя с номером компонента; после удаления фокус на соседней строке или добавлении. Поля скрытой строки не блокируют отправку. |
| UI-02 | Узкий экран и масштаб | На 360, 768 и 1280 CSS px и при масштабе 200% доступны добавление, удаление, пересчёт, сохранение, отмена и выход. Нет горизонтальной прокрутки всей страницы; широкая таблица прокручивается внутри собственного блока. Длинные названия/ошибки не перекрывают кнопки. |
| UI-03 | Читаемость | Обычный значимый текст имеет контраст не ниже 4,5:1, крупный — 3:1; проверяются реальные пары текста и фона. Зоны и ошибки обозначены текстом, а не одним цветом. Для основных кнопок проекта целевая высота — не менее 44 CSS px. |
| UI-04 | Состояния | Проверяются пустой справочник, нормальный экран, ошибка, конфликт, предпросмотр, устаревший предпросмотр, успешное сохранение. Успех показывается только после фиксации; ограничение не выглядит как молча неработающая кнопка. |

Порог контраста взят из [пояснения W3C к WCAG 2.2 SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). Высота 44 px — выбранный ориентир удобства кнопок проекта, не утверждение о минимуме уровня AA: [SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) описывает минимум 24×24 px с исключениями. Проверка перечисленных пунктов не означает сертификацию всего продукта по WCAG.

## Независимая проверка на каждом этапе

1. Исполнитель перечисляет изменённые сценарии и связанные ID из этой таблицы, выполняет необходимые серверные/расчётные проверки на тестовой БД.
2. Агент, не писавший изменения, проверяет поток действий и читаемость состояний; второй отдельно проверяет клавиатуру, узкую ширину и визуальную иерархию. При изменениях сохранения отдельный рецензент проверяет данные и журнал.
3. Браузерный прогон выполняется на изолированных QA-данных: мышь, клавиатура, узкий экран, один ошибочный ввод, отмена и повторное подтверждение. Пользовательская база не используется для тестовых записей.
4. Для каждого ID фиксируются «проверено автоматически», «проверено в браузере», «проверено чтением кода», «дефект» или «не проверено». Нельзя заменять фактический визуальный прогон чтением CSS/HTML.
5. Проблемы расчёта, потери данных и недоступные основные действия исправляются до приёмки. Остальные замечания получают явный статус и привязку к этапу. Затем заказчик проверяет короткий пользовательский сценарий.

После каждого этапа 3–6 проверяются изменённые экраны и базовый путь создания рецептуры. На этапе 7 — полный проход всех пунктов на компьютере и телефоне. Оформление разницы округления по-прежнему согласуется отдельно перед этапом 5.

## Базовая проверка 04.11.2026

Этот раздел описывает предыдущие правки. Приведённые результаты не подтверждают добавленные в редакции 2 UX-07–08 и ED-08–12.

Три независимых агента проверили требования/UX, UI/доступность и влияние изменений на расчёты/данные. Статический просмотр выявил обязательного поставщика, чекбокс удаления, скрытый мобильный выход, слабый контраст подсказок, отсутствие пометки устаревшего расчёта и молчаливый предел строк. Эти места исправлены в текущей правке.

При повторном ревью найден и исправлен риск удаления первой строки по Enter: безопасное действие по умолчанию теперь расчёт. Регрессия проверяет первую submit-кнопку и соответствующий POST для блюда и заготовки; фактическое поведение Enter в браузере остаётся в ручном прогоне.

Итоговые проверки: **127 passed in 22.38s**, 16 проверок точного перевода единиц, JavaScript syntax check, Django system check и отсутствие расхождений моделей/миграций. Три рецензента после исправлений блокеров не выявили. Миграция 0005 применена после резервной копии `.local/backups/tseh-20261104T145810054299Z.dump` и успешного пробного восстановления; существующие связи поставщиков покрыты миграционной регрессией. Тестовые записи в пользовательскую базу не добавлялись.

## Текущий прогон обновления/черновика

Для новой и существующей рецептуры: изменить поля и строки → F5 → проверить восстановленный ввод → «Обновить данные» → новый предпросмотр → сохранить → проверить очистку именно сохранённого варианта. Повторить после ошибки, с правкой базы другой вкладкой, недоступным хранилищем, отменой и подтверждением «Сбросить черновик». Проверить выравнивание названия/выхода/единицы с многострочными подписями и ошибками.

Фактический браузерный прогон пока **не выполнен**: browser host недоступен, затем native tool остановился на проверке уверенности в URL. F5, вкладки, реальные viewport и верхняя сетка не объявляются проверенными. Автоматические/статические результаты новой реализации должны быть записаны отдельно после её проверки.

Результат текущей реализации 0.2.3: **164 серверных теста прошли за 32.17 s** в изолированной тестовой БД; 16 проверок точного перевода единиц, 10 групп проверок хранилища и 20 сценариев контроллера на модели DOM прошли через Node. Последние проверяют реальные функции контроллера, включая повтор старого POST, недоступный компонент, отказ хранилища и обработчики BFCache, но не заменяют браузер. Синтаксис JavaScript проверен. Статический Impeccable scan не выдал замечаний; анализ связанного CSS ограничен нераспознанным Django static-тегом, CSS проверен также отдельным файлом. Независимое ревью выявило и помогло закрыть риски повторного появления черновика из BFCache и сброса повреждённой копии без подтверждения. Пользовательская визуальная приёмка остаётся открытой.

## Исследование кнопок после обратной связи, 04.11.2026

Заказчик повторно отметил ощущение смещения текста. Формулировка предыдущего отчёта «исправлены оптическое выравнивание» не означает принятия внешнего вида: вариант 0.3.2 пользователем не принят. Правило `ex alphabetic` в DESIGN.md — текущая реализация, а не доказанная норма оптического центрирования.

Два независимых агента выполнили разные проверки: `button_guidelines` изучил официальные источники и контекст продукта; `button_metrics` измерил действующий интерфейс в Chrome 157 / Windows / DPR 1. Их выводы сопоставлены координатором. Исследование не меняет расчёты, рабочие данные или стили приложения.

### Что подтверждено

- Фактический шрифт — Segoe UI 600, 14 px; иконка — 16 px. Кнопки имеют высоту 48 px, симметричные вертикальные отступы 12 px. Ошибки flex-центрирования контейнера не найдено.
- Текущий `ex alphabetic` центрирует блок высотой 7 px; `cap alphabetic` — около 9,80 px; обычная строка — 20 px. Это метрики шрифта, а не границы фактически нарисованного слова.
- Расчёт относительно контура букв дал для «Показать» положение примерно на 1,5 px выше центра при `ex`, около центра при `cap` и обычной строке. Для «Пересчитать» переход на `cap` или обычную строку, напротив, опускает контур примерно на 1,4–1,5 px ниже центра. Это диагностические измерения, не оценка удобства человеком.
- Центр массы отрисованных пикселей и центр ограничивающего прямоугольника букв дают разные оценки. Дробные координаты и округление до пикселей влияют на небольшой текст. Ни `ex`, ни `cap`, ни индивидуальная поправка для каждого слова не являются универсальным решением.

Основание терминов: [W3C CSS Inline Layout — метрики и обрезка текстового блока](https://www.w3.org/TR/css-inline-3/#text-box-trim), [MDN text-box-edge](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-box-edge). [Chrome guidance](https://developer.chrome.com/docs/modern-web-guidance/guides/visual-design/precise-text-alignment) рекомендует `cap alphabetic` как исходный вариант для многих UI-сценариев, но это не доказательство его превосходства на конкретных русских подписях Цеха.

### Skills и правила

[Anthropic frontend-design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md) изучен как источник, без установки. Он полезен для согласованной типографики, иерархии, работы с токенами и проверки результата по снимку. Специальной формулы центрирования русских кнопок в нём нет. Impeccable в режиме Operate уже даёт подходящую основу для рабочего сервиса; добавление ещё одного skill не заменяет визуального выбора и приёмки.

Для компонентов сохранять общий шрифт, понятный регистр и действие в подписи, видимый фокус, различимые состояния, рост высоты при переносе, проверку русских строк и увеличения до 200%. Размеры 48/16/8/6 px — решения проекта, не универсальный стандарт. [GOV.UK](https://design-system.service.gov.uk/components/button/) рекомендует описывать действие обычным регистром; [Fluent](https://fluent2.microsoft.design/components/web/react/core/button/usage/) — выделять одно главное действие и снижать вес множества второстепенных.

### Проверяемые варианты и следующие улучшения
