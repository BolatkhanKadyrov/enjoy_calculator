## Проверки, требующие завершения этапа 7

На первом проходе дефектов бизнес-расчётов или потери данных не обнаружено. Ни одна из 27 групп не остаётся полностью без реализации/проверки. Следующие границы нельзя скрывать общим числом прошедших тестов:

1. **Production-доступ.** В этапе 7 стандартный вход заменён ограничителем PostgreSQL: резервирование до проверки пароля, 10 попыток за 5 минут на источник, 429/Retry-After, HMAC вместо исходного IP. Независимое чтение `auth.py`, модели/0012 и `test_auth_security.py` не выявило блокеров: параллельные первые запросы сериализованы, успех возвращает только собственную попытку своего окна, JSON-восстановление не сбрасывает счётчик, действующие сессии общей учётной записи остаются рабочими. **18 auth-тестов** вошли в общий прогон. Proxy trust теперь явный opt-in; доверять X-Real-IP/X-Forwarded-Proto можно только за единственным ingress, который перезаписывает их. Cookies/CSRF/no-store и верхние границы настроек проверены конфигурационными тестами; production `check --deploy` оставляет два ожидаемых предупреждения W005/W021: HSTS includeSubDomains/preload намеренно не включены без оценки домена. Распределённую атаку с многих адресов и полноценный pentest этот контроль не обещает.
2. **Миграции/эксплуатация.** Тесты миграций проверяют сохранение рецептур, цен, истории, учётной записи; в этапе 6 локальная рабочая миграция выполнена после pg_dump и настоящего пробного восстановления. Этап 7 проверяет pre-deploy на PostgreSQL и launcher через Git shell. Пока не подтверждены реальный Linux production image, внешний ingress/PostgreSQL/TLS, healthcheck Railway и расписание очистки. Первые проверки возможны локально на машине с Docker; внешние — только после разрешения размещения. JSON не сохраняет auth и не заменяет PostgreSQL backup перед миграцией.
3. **Вывод и интерфейс.** Проверка XLSX в настоящем Excel/LibreOffice и полный screen-reader/масштабный обход остаются явно не выполненными; это границы доказательств, а не найденные блокеры подготовки Railway. Статические HTML/CSS, Node DOM и openpyxl не подменяют такие проверки. Пользовательская приёмка остаётся отдельной от агентского ревью.
4. **Пределы надёжности.** Временная предимпортная копия PostgreSQL живёт 24 часа; экспортируемый JSON ограничен 25 МиБ/50 000 записей. Регулярные внешние резервные копии и хранение вне контейнера — эксплуатационная процедура, сейчас не созданные внешние ресурсы. Глобальная блокировка DomainState делает чтение/запись согласованными, но при росте нагрузки сериализует операции; целевой последовательный тест этого не маскирует.

## Пять браузерных сценариев для приёмки

Все мутации — только в изолированной QA-базе. Для сценариев 1/2/5 нужны desktop и 360 px, видимый фокус и увеличение 200%; широкие таблицы могут прокручиваться внутри блока, вся страница — нет.

Это перечень для приёмки, не утверждение о новом полном ручном прогоне. Координатор этапа 7 сообщил фактически выполненное после QA-миграции 0012: выбор компонента клавиатурой, **125,5 г муки → свежий GET с восстановленным черновиком → предпросмотр 69,03 → сохранение → мобильная карточка**; мобильный сценарий цены муки **550→600**; **11-я ошибка входа → 429/Retry-After**, чистые поля, фокус на ошибке, отсутствие overflow при 360 px, успешный вход после истечения окна. Остальные сценарии имеют свидетельства прошлых этапов и полного набора автотестов; повтор каждого вручную в этапе 7 не заявлен.

1. Создать сырьё без поставщика → вложенную заготовку → блюдо с упаковкой. Поиск компонента клавиатурой, автоматическая единица, точный ввод и ошибка размерности, удалить/добавить строку. F5/«Обновить данные» восстанавливают черновик, затем новый расчёт и сохранение; явный сброс отдельно подтверждается. Проверить скидку, зоны, долю, минимальную цену и уникальное сырьё.
2. Закупка с доставкой и повтором позиции → предложения → совокупный сценарий **269→306→304**. Исключить масло, отменить, снова применить; состав закупки/доставка не меняются от исключения применения. Исправить историческую цену и проверить даты/журнал; увидеть отдельное пояснение округления и три варианта удаления строки.
3. Две вкладки/два входа: открыть одну закупку, в первой изменить доставку, во второй подтвердить старую. Второй запрос объясняет конфликт, данные первого сохранены; повтор подтверждения не дублирует событие. Старый сценарий также отвергается, ввод доступен для пересчёта.
4. Скачать JSON → изменить QA-данные → загрузить копию → скачать предимпортную копию → подтвердить. Убедиться, что состав/суммы/журнал восстановлены, вход сохранён, старая вкладка не может записать старую epoch. Обновить предкопию в другой вкладке: прежнее подтверждение должно требовать нового просмотра/скачивания.
5. Архив → корзина → восстановление в архив → отдельная активация. Используемый справочник показывает связи и не переносится, неиспользуемый восстанавливается из бессрочной корзины. Скачать JSON/XLSX, выйти; повторно открыть защищённый адрес/скачивание без входа нельзя. В XLSX вручную проверить заголовки, единицы, скидку, даты и известную сумму.

Ожидаемые числа в расчётных тестах — буквальные примеры исходных критериев/самостоятельные эталоны, а не результат вызова проверяемого кода. Исключение по форме, но не по независимости: P_min дополнительно сравнивается с отдельным исчерпывающим Decimal-перебором. Новый тест масштаба использует заранее выведенные **500/500/600** за кг заготовок и **560** за порцию; production-ядро не вычисляет ожидаемое значение теста.

## Независимое ревью production-упаковки

Прочитаны `Dockerfile`, `.dockerignore`, `config/build_settings.py`, `scripts/start-production.sh`, `scripts/predeploy.py`, [инструкция Railway](railway.md) и соответствующие тесты. `railway.json` удалён: [официальная документация Railway](https://docs.railway.com/config-as-code) подтверждает, что новые сервисы уже не могут использовать legacy Config-as-Code. Вместо непроверенного SDK даны точные UI-настройки будущих web/maintenance-сервисов. На этом проходе:

- Build-контекст разрешает только необходимые исходники; локальные БД, `.env`, резервные копии и браузерные профили в образ не попадают. Статика собирается без production-секретов и соединения с БД. Runtime работает от UID/GID 10001, исходники и окружение доступны на чтение; временные загрузки используют системный `/tmp`.
- Web запускает Gunicorn с проверенными числовыми PORT/workers/threads/timeout, без автоматических миграций/создания учётной записи. `exec` сохраняет сигналы/exit status; access log не включает query string, cookies и body. Доверие proxy не дублируется второй независимой настройкой Gunicorn.
- Pre-deploy берёт advisory lock на релиз и блокировку DomainState до изменения схемы; атомарная транзакция охватывает миграции и повышение revision. Ошибка откатывает DDL/данные, закрытие соединения освобождает advisory lock. Конкурирующий релиз и неатомарная миграция отвергаются. Текущая 0012 только добавляет таблицу и совместима с ещё живой старой версией; это не гарантия совместимости любых будущих миграций.
- Maintenance выполняет очистку корзины блюд, временного восстановления, счётчиков входа и истёкших сессий; завершается, прекращая цепочку при ошибке. Каталожную корзину автоматически не очищает.

Блокирующих дефектов в прочитанной реализации и окончательной инструкции не найдено. Независимо сверены официальные страницы Railway о legacy Config-as-Code, pre-deploy timeout, cron CLI и proxy-заголовках; ссылки включены в инструкцию. Runbook разделяет JSON и PostgreSQL dump, требует настоящего пробного восстановления и смены epoch/удаления старых технических квитанций после полного dump restore при остановленных writers. Ежедневное обслуживание назначается на 02:00 UTC и проверяется по успешному запуску, не по факту deploy.

Docker/WSL на этой машине отсутствуют: проверка POSIX-launcher под Git shell, Python и PostgreSQL-тесты не заменяют реальный запуск Linux-образа. Внешние ресурсы/расписание/развёртывание не создавались. Будущая несовместимая миграция требует специального окна или совместимого перехода; откат образа приложения не откатывает уже зафиксированную БД.
