# Решения после редакции 3

Основание — ответы заказчика в текущем чате. Исходные три документа сохранены без изменения.

1. Повторные строки одного товара в одной закупке объединяются в средневзвешенную цену базовой единицы: сумма стоимости товара и сохранённых долей доставки / общее количество базовых единиц. Доставка сначала распределяется по полному составу закупки. Исходные строки сохраняются. Пример: 2 кг × 1000 + 8 кг × 1500 = 14000 за 10 кг, цена 1400/кг. Усреднение между разными закупками не добавляется. Выбор действующей цены остаётся явным.
2. Прямой ввод некорректной пары порогов отклоняется. Уже согласованный конфликт наследования после изменения общих порогов сохраняется и восстанавливается из JSON без цвета, с видимыми C и r.
3. При некорректной итоговой паре P_min не отображается до исправления.
4. Оформление разницы округления согласовать с заказчиком **перед этапом 5**. Предложенная отдельная строка пока не утверждена.
5. План реализации согласован, старт разрешён. Этапы завершаются независимым ревью и пользовательской приёмкой. Размещение и создание внешних ресурсов не разрешены текущим поручением.
6. Уточнение заказчика 04.11.2026: при добавлении сырья поставщик необязателен. Цена хранит nullable-ссылку; фиктивный поставщик не создаётся. Та же форма для упаковки допускает отсутствие поставщика. Фасовка, первая действующая цена, дата и аудит остаются обязательными. Существующие ссылки на поставщиков сохраняются. Это уточнение имеет приоритет над прежней обязательностью поставщика; исходные документы не переписываются.
7. Удаление компонента блюда/заготовки выполняется кнопкой, без чекбокса. Меняется редактируемый состав; сохранение остаётся явным после нового расчёта. Введён регулярный независимый UX/UI-контроль по `ux-ui-acceptance.md`.
8. Заказчик разрешил поручать агентам и субагентам реализацию задач. Работа ведётся с разделением владения файлами и независимым ревью; координатор собирает результат и проверяет его целиком. Порядок — `team-workflow.md`. Это не меняет границы версии и не разрешает внешнее развёртывание.
9. Уточнение заказчика 04.11.2026: работа в редакторах блюда и заготовки должна сохраняться при F5/обновлении. Возвращается отдельное действие «Обновить данные», сохраняющее черновик; «Сбросить черновик» означает явное удаление несохранённого варианта с подтверждением. Это заменяет прежнее объединение перечитывания формы и сброса в одном действии. Формулы и явное сохранение рецептуры в БД не меняются.

## Техническое решение: черновик редактора

- Область — только редакторы рецептур блюд и заготовок. Черновик хранится в `sessionStorage` отдельно по учётной записи и пути формы, в пределах вкладки. Это локальное сохранение ввода, не доменная запись, журнал или резервная копия. Сохранность после закрытия вкладки не гарантируется; без JavaScript автоматического восстановления нет.
- Сохраняются разрешённые поля, полный состав и порядок строк, количества строками и связанные единицы. Не сохраняются CSRF, токены команд/предпросмотра, вычисленные суммы или готовый HTML. Метаданные исходных revision/epoch нужны только для предупреждения об изменении базы и не дают права записи.
- На свежем GET черновик восстанавливается без прежнего предпросмотра; перед сохранением обязательны новый расчёт по текущим данным и подтверждение. Если исходные revision/epoch отличаются, показывается предупреждение. Свежий токен не разрешает молчаливую запись старого черновика; обычная серверная защита конкурирующих правок сохраняется.
- Первый ответ на последнюю отправку POST имеет приоритет над отправленной локальной копией, чтобы не затереть серверную нормализацию единиц и ошибки. Отправки сопоставляются по случайному идентификатору, не дающему права записи. Если F5 повторяет старый POST после более поздних правок, восстанавливается актуальный локальный ввод с аннулированием предпросмотра. Пропавший компонент не заменяется автоматически и не удаляется из черновика молча.
- «Обновить данные» сначала записывает черновик, затем загружает свежую форму. При ошибке записи в хранилище показывает сообщение и не переходит на другую страницу. Нативный F5 при недоступном хранилище нельзя объявлять защищённым от потери ввода.
- Очистка выполняется после явного подтверждения сброса либо подтверждённого успешного сохранения. Сигнал успеха должен совпадать с соответствующим черновиком/отправленным вариантом: старый ответ не удаляет более новый ввод. Сам submit, ошибка или потеря ответа не очищают черновик.
- Копия вкладки может получить первоначальную копию `sessionStorage`; дальнейшие правки не должны смешиваться. Разные аккаунты/формы не подхватывают чужой черновик. Нельзя обещать общий черновик для всех активных входов.

Статус этого решения — спецификация текущей правки, не отчёт о пройденных тестах. Browser host недоступен; попытка через native tool остановлена проверкой уверенности в URL. Визуальные проверки, F5 и поведение вкладок в реальном браузере не выполнены. Критерии — ED-08–12 в `design-editor.md`.

## Технические решения этапа 1

- Django 5.2 LTS, PostgreSQL, серверные формы. UI не вычисляет денежные суммы. Точный состав зависимостей зафиксирован в requirements.lock.
- Одна организация, KZT, конечные цены без налоговой модели; UTC в БД, Asia/Qyzylorda по умолчанию для отображения.
- Денежный ввод: до 12 целых и 2 дробных знаков. Фасовки/количества: до 12 целых и 12 дробных. Потери: до 8 дробных, 0 <= p < 100. Лишние знаки отклоняются, а не усекаются.
- Ввод и хранение — Decimal / NUMERIC. Деления и итоговая денежная граница — точные рациональные числа из десятичных входов. Это обеспечивает 0.01 / 3 × 16.5 = 0.055 → 0.06 без погрешности конечного контекста Decimal. Float не используется.
- Исходные единица и количество рецептуры сохраняются; нормализация происходит в ядре. 0.004 кг отображается как 4 г. Открытие/сохранение не сокращает точность.
- Короткая блокировка единственной строки состояния обеспечивает согласованные снимки и фиксацию команд. Общая ревизия консервативно отклоняет в том числе некоторые несвязанные правки. Во время редактирования в браузере блокировки нет.
- Идентификатор подтверждения + отпечаток содержимого предотвращают повторную запись и подмену повторного запроса. Поколение данных отделено от ревизии для будущего восстановления.
- Ингредиент и первая цена создаются с отложенными FK в одной транзакции. Составной FK проверяет принадлежность действующей цены ингредиенту. Журнал и событие применения входят в ту же транзакцию.

## Технические решения этапа 2

- Заготовки образуют направленный граф без циклов; расчёт выполняется от сырья к зависимым заготовкам и блюдам. Стоимость единицы определяется введённым выходом. Первичные потери применяются только к исходному сырью, повторно на уровне заготовки не добавляются.
- Упаковка — отдельный тип закупаемой позиции с обязательными нулевыми потерями. Используется в блюдах, не в заготовках. Созданный тип позиции не меняется через редактирование.
- Для количества рецептуры и выхода хранение расширено до NUMERIC(30,15). Проверка происходит в базовой единице: значение положительно, меньше 10^12, не более 15 дробных знаков; избыточная точность отклоняется. Это сохраняет исходные значения этапа 1 при точном переключении г/кг и мл/л. Фасовки сохраняют прежний формат. Исходная единица сохраняется; преобразование количества выполняется также сервером при отключённом JavaScript.
- Скидка анализа хранится в пользовательской сессии и не меняет отпускную цену или доменный журнал. В расчёте используются округлённые C и P_eff, сравнение с порогами — точное, отображённый процент не участвует в сравнении.
- Каждый порог блюда независимо наследуется из общих настроек или задан явно. Значение больше 100% разрешено с предупреждением. При наследованном конфликте разрешены несвязанные изменения рецептуры, сохраняющие существующие пороги; новый прямой ввод конфликтной пары отклоняется.
- P_min ищется по сетке 0,01 с учётом округления P_eff и его положительности. Для расчёта нужен G; отсутствие O не мешает расчёту P_min, но цвет без полной пары не назначается. При некорректной полной паре P_min скрыт по решению заказчика. Верхняя граница цены соответствует допустимому денежному вводу; превышение показывается отдельно.
- Перед обновлением локальной рабочей схемы приложение останавливается после проверки принадлежности процессу проекта; выполняются pg_dump и настоящее пробное восстановление в отдельную временную БД. Доменная ревизия повышается, чтобы старые формы не применялись после миграции. Это техническая копия PostgreSQL, не пользовательский JSON-экспорт этапа 6.

## Утверждённая типографика и следующий этап

04.11.2026 заказчик выбрал вариант D: кнопки Segoe UI 16 px / 20 px, обычная строка без обрезки метрик, минимальная высота 48 px. Согласовано применить рекомендации по компактной шапке, иерархии действий, единым подписям и затем перейти к этапу 4 (закупки и доставка). Пользовательская оценка D завершена выбором; проверка реализации и приёмка закупок остаются отдельными шагами. Контроль перед этапом 5 сохраняется.


Технические решения этапа 4: исходные строки закупки сохранены; одна связанная запись цены на позицию хранит точные суммы стоимости/количества и распределённой доставки, цена единицы вычисляется Fraction. Простая цена без доставки и повторов не требует количества упаковок; расчётные основания такой цены не выдаются за физический закупленный объём. Исправление обновляет прежний Price ID и связанные точки истории. Удаление последней строки атомарно удаляет пустую закупку. Цены из закупки изменяются через её состав, не через форму одиночной цены. Новая закупка сохраняет предложения без автоматического применения.

После удаления только доли строки остальные доли сохраняются буквально. Повторное сохранение без финансовых изменений, правка описания/даты/поставщика и перенос нулевой доставки не должны сдвигать их на копейку. Изменение состава, фасовки, цены, количества или общей доставки перераспределяет всю закупку. Это сохраняет результат выбранного действия и исключает финансовые изменения при неизменном вводе.


Последующее решение заказчика: вариант D оказался слишком заметным в реальном интерфейсе. Применить C: 14/20 px, обычная строка без text-box-trim; высота 48 px и остальные состояния сохранены. Проверить весь текущий проект с независимых сторон перед этапом 5. Утверждение D выше остаётся историей, актуальный вариант — C.


Перед этапом 5 заказчик согласовал отдельное пояснение и поправку «Разница из-за округления». Она не относится к ингредиенту и не меняет расчёты. Экранная поправка = (окончательная C_new − окончательная C_old) − сумма округлённых показываемых вкладов. Если точная сумма вкладов отличается от разницы итогов, пояснение показывается даже при нулевой экранной поправке. Изменения меньше 0,01 ₸ объясняются текстом; обычные денежные колонки остаются с двумя знаками.

Технические границы сценария 5: изменяемый набор новых либо сохранённых цен; ровно одна предлагаемая цена на позицию. Подготовка закупки и доставки остаётся отдельным явным сохранением предложений этапа 4. Сценарий можно начать набором цен уже сохранённой закупки; удаление изменения из набора не меняет её исходные строки, цены и распределение. Просмотр/отмена сценария не создают цены или историю. Набор применяется полностью атомарно; постоянной модели черновика Scenario не требуется. Изменение рецептур остаётся в существующих редакторах с предпросмотром, совмещать его с ценами в одну операцию не требуется исходным заданием.

## Уточнения этапа 6 — 05.11.2026

Заказчик разрешил реализацию следующего этапа и уточнил:

1. Уникальность сравнивается только с другими активными блюдами. Архив и корзина не уменьшают уникальность активного ассортимента. Для просмотра неактивной карточки сравнение также делается с активными блюдами.
2. В общую корзину добавляются сырьё/упаковка, заготовки и поставщики. Нужны поиск, фильтры и сортировка.
3. Перенос используемой записи в корзину блокируется с показом связей. Учитываются рецептуры любого состояния, закупки и связи с ценами. Собственные цены сырья не являются внешним использованием: они сохраняются вместе с позицией в корзине.
4. Корзина справочников бессрочная, до явного окончательного удаления. Восстановление возвращает запись в соответствующий справочник. Правило 30 дней для блюд остаётся прежним.

Технические решения: поля состояния/исторической даты корзины у справочников; недоступность записей корзины для новых ссылок. При явном окончательном удалении неиспользуемого сырья удаляются его собственные цены и применения, а полный снимок сохраняется в журнале. Связанные рецептуры или закупки каскадно не удаляются.

JSON формата 1 сохраняет все доменные сущности без учётных записей, сессий и технических квитанций. Временная подготовка восстановления хранится в PostgreSQL 24 часа. Подтверждение связано с пользователем, загруженным файлом и конкретной предимпортной копией; обновление копии требует нового подтверждения, в том числе между вкладками. При замене создаётся новая epoch. Остаток срока блюд сохраняется в микросекундах; каталожная корзина срока не имеет. Лимиты JSON: 25 МиБ, 50 000 записей, глубина структуры 32. XLSX — статический отчёт с ограниченной точностью Excel; зависимость openpyxl 3.1.5 зафиксирована.

## Технические решения этапа 7 — 05.11.2026

Заказчик разрешил самостоятельное продолжение следующего этапа на время отсутствия. Это разрешение на реализацию/проверку и подготовку размещения; ранее установленная граница внешних ресурсов и публикации не отменена.

- Защита входа выбрана исполнителем: 10 попыток за фиксированные 300 секунд на источник, счётчик в PostgreSQL. Успех освобождает только свою попытку. Учётная запись глобально не блокируется; действующие сессии сохраняются. Хранится HMAC адреса (IPv6 объединяется до /64), не исходный IP. Лимиты настраиваемы в технических границах 1–1000 и 1–86400 секунд. Это не новое бизнес-правило расчёта.
- Доверие proxy по умолчанию выключено, на Railway включается только после проверки единственного очищающего заголовки HTTP ingress. Нет автоматического доверия цепочке X-Forwarded-For. Production требует HTTPS, явных hosts и сильного отдельного секрета; данные не кешируются как публичные ответы.
- Docker/Gunicorn, отдельный predeploy с advisory/DomainState lock и атомарными миграциями, отдельный maintenance без web. Новые миграции и смена image не означают автоматического безопасного отката БД. Полный PostgreSQL restore требует новой epoch и удаления технических подтверждений/сессий до открытия доступа.
- Локально проверены код, PostgreSQL и POSIX-команды через Git shell. Docker/WSL недоступны; Linux и реальные Railway ingress/cron пока не подтверждены. Не создавать legacy railway.json для нового сервиса: текущая официальная документация его больше не допускает; точные UI-настройки в `railway.md`.
- Итоговые свидетельства и пользовательская приёмка — `stage-7-verification.md`, соответствие всем критериям — `stage-7-acceptance-matrix.md`. Новые функции из бэклога не добавлены.
