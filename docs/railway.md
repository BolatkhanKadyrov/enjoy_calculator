# Railway: запуск и эксплуатация

Подготовлено 5 ноября 2026 года. Приложение на Railway не развёрнуто. Эта инструкция описывает будущий запуск после согласования. После публикации исходников сборка Linux-образа и запуск Gunicorn с PostgreSQL 17 проверены в GitHub Actions — [отчёт CI](github-verification.md). Реальный ingress и расписание Railway ещё требуют проверки. На рабочем Windows-компьютере Docker отсутствует, WSL не установлен.

## Состав окружения

Для первой версии достаточно одного web-сервиса с одной репликой, PostgreSQL 17 и отдельного короткоживущего сервиса ежедневного обслуживания. Web использует Python 3.14, Django, Gunicorn и WhiteNoise. Версии Python-пакетов зафиксированы в `requirements.lock`; Python-образ — `python:3.14.6-slim-bookworm`. Это выбранная проверенная локально версия Python, а не заявление о последней доступной версии. Базовый образ берётся из [официального репозитория Python](https://hub.docker.com/_/python).

Все доменные данные, история, пользователи, сессии и временные подготовки JSON-восстановления находятся в PostgreSQL. Web не требует постоянного тома: static входит в образ, скачиваемые файлы формируются по запросу, временные файлы контейнера не являются резервной копией. Обе службы должны обращаться к одной БД. Не подключать SQLite или рабочую локальную БД.

Railway объявил старый `railway.json` / `railway.toml` устаревшим: новые сервисы уже не могут его включить; для прежних заявлена граница 1 декабря 2026 года. Поэтому legacy-конфигурация не добавлена. Ниже приведены точные настройки сервисов через UI. При будущем подключении IaC следует импортировать фактическое окружение и проверить план; непроверенный SDK и команда создания ресурсов в проект не включены. Источники: [Railway Config as Code](https://docs.railway.com/config-as-code), [актуальный IaC](https://docs.railway.com/infrastructure-as-code).

## Сборка образа

Из корня проекта на машине с Docker:

```sh
docker build --pull -t tseh:release .
```

Команда не требует `DATABASE_URL` и production-секрета. Build-стадия использует только `config.build_settings`, который разрешает `collectstatic` и запрещает применение как runtime settings. Тест отдельно запрещает любые подключения к БД во время сборки static. В финальном образе применяется `config.settings`; фиктивные build-переменные не переходят в runtime. `.dockerignore` включает только необходимые исходники, исключая `.env`, локальную БД, резервные копии, `.venv`, Git и пользовательские файлы.

Установка использует фиксированный lock-файл и только готовые wheels; отсутствие wheel для выбранной Linux-архитектуры остановит сборку. Используется Linux-интерпретатор из образа, локальная Windows `.venv` не переносится; платформенные установки описаны в [документации Python 3.14](https://docs.python.org/3.14/using/unix.html). Перед первым релизом нужно выполнить именно Linux-сборку и smoke-тест, сохранить digest полученного образа и digest проверенного базового образа. Для повторения сборки с тем же базовым образом используйте `--build-arg PYTHON_IMAGE=python:3.14.6-slim-bookworm@sha256:ПРОВЕРЕННЫЙ_DIGEST`. До фиксации digest тег базового образа может обновиться; битовую идентичность пересборок инструкция не обещает.

Static собирается один раз при build, включая хешированные и сжатые версии; после запуска его обслуживает WhiteNoise. Runtime работает пользователем UID/GID 10001, не root. Gunicorn запускается через `exec`, получает сигналы контейнера и слушает `0.0.0.0:$PORT`. Основания: [Django deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/), [WhiteNoise для Django](https://whitenoise.readthedocs.io/en/stable/django.html), [настройки Gunicorn](https://gunicorn.org/reference/settings/).

## Переменные окружения

Задать в Railway Variables; `.env.example` — пример, автоматического чтения `.env` нет. Секреты не передавать build arguments и не помещать в Git.

| Переменная | Значение / назначение |
|---|---|
| `DATABASE_URL` | Ссылка на PostgreSQL 17 этого окружения через private network Railway; в UI обычно `${{Postgres.DATABASE_URL}}`, с фактическим именем сервиса БД |
| `DJANGO_SECRET_KEY` | Один случайный секрет не короче 50 символов; одинаковый для web и обслуживания; хранить отдельно от репозитория |
| `DJANGO_DEBUG` | `0` |
| `DJANGO_ALLOWED_HOSTS` | `ФАКТИЧЕСКИЙ_ДОМЕН,healthcheck.railway.app` без схемы, пути и `*` |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | `https://ФАКТИЧЕСКИЙ_ДОМЕН`; дополнительные разрешённые домены перечислить через запятую |
| `DJANGO_SECURE_SSL_REDIRECT` | `1` |
| `DJANGO_TRUST_PROXY` | `1` только при подтверждённом доверенном ingress, описанном ниже |
| `TZ` | `Asia/Qyzylorda` |
| `PORT` | Значение Railway; launcher использует его напрямую. Вне Railway по умолчанию `8000` |
| `WEB_CONCURRENCY` | По умолчанию `2` процесса; допустимо 1–16 |
| `GUNICORN_THREADS` | По умолчанию `2` потока на процесс; допустимо 1–8 |
| `GUNICORN_TIMEOUT` | По умолчанию `120` секунд; допустимо 10–600 |
| `DJANGO_LOGIN_MAX_ATTEMPTS` | По умолчанию `10` попыток в окне |
| `DJANGO_LOGIN_WINDOW_SECONDS` | По умолчанию `300` секунд |

Количество процессов и потоков — начальная настройка, не результат нагрузочного измерения. Следить за памятью и соединениями PostgreSQL при JSON/XLSX-экспорте. Один web-контейнер не означает один поток; защита изменений и ограничение входа используют общую БД. Gunicorn `timeout` для `gthread` не является точным дедлайном каждого HTTP-запроса.

`DJANGO_TRUST_PROXY=1` доверяет `X-Forwarded-Proto` для HTTPS и `X-Real-IP` для ограничения попыток входа. Это допустимо, только если Railway public HTTP edge — единственный публичный вход и он перезаписывает оба заголовка. Не открывать TCP proxy к web и не направлять через него непроверенные внутренние запросы. Gunicorn сам не доверяет forwarded-заголовкам (`--forwarded-allow-ips ''`), чтобы второй независимый путь доверия не менял протокол. Django отдельно предупреждает, что доверять таким заголовкам можно лишь после проверки поведения прокси: [SECURE_PROXY_SSL_HEADER](https://docs.djangoproject.com/en/5.2/ref/settings/#secure-proxy-ssl-header).

Перед первым публичным запуском проверить на staging вход через настоящий edge: HTTPS не зацикливает redirect, secure cookies работают, подставленные клиентом `X-Forwarded-Proto` и `X-Real-IP` не меняют определённый сервером протокол/IP. Проверку IP и лимитера проводить на отдельной тестовой учётной записи; неправильная настройка может либо обходить квоту, либо объединять пользователей в одну квоту. Публичные ограничения и заголовки описаны в [Railway networking](https://docs.railway.com/networking/public-networking/specs-and-limits); этот сетевой контракт ещё не проверен фактическим запросом данного приложения.

## Настройки web-сервиса

Создание сервисов и домена — отдельное действие после разрешения владельца. Выбрать регион, доступный обоим сервисам и PostgreSQL, и PostgreSQL major 17; не оставлять неподтверждённый `latest` БД. В UI web задать:

| Настройка | Значение |
|---|---|
| Source / Root Directory | Репозиторий и его корень |
| Builder | Dockerfile |
| Dockerfile path | `Dockerfile` |
| Custom Build Command | Пусто: команды находятся в Dockerfile |
| Pre-deploy Command | `python scripts/predeploy.py` |
| Pre-deploy Timeout | `300` секунд |
| Start Command | `sh scripts/start-production.sh` |
| Healthcheck Path | `/health/` |
| Healthcheck Timeout | `300` секунд |
| Restart Policy | On Failure, не более 3 повторов |
| Replicas | 1 |
| Cron Schedule | Пусто |
| Volume | Не требуется |
| Public Networking | HTTPS-домен Railway либо согласованный собственный домен; target port соответствует `PORT` |

При первичной настройке не запускать deploy до заполнения обязательных переменных, подключения БД и проверки настроек. Start command не запускает миграции, не создаёт пользователя и не добавляет демо. Перезапуск web повторно запускает только Gunicorn. При неуспешном predeploy Railway останавливает релиз; сам predeploy не повторяется автоматически. Он исполняется в отдельном контейнере, без смонтированного тома; поэтому резервную копию нельзя оставлять в его файловой системе. Источник: [Railway pre-deploy](https://docs.railway.com/deployments/pre-deploy-command).

`/health/` доступен без входа, проверяет соединение с БД и возвращает короткий статус; он не выдаёт доменные данные. Для HTTP-пробы исключение из HTTPS redirect ограничено точным `/health/`. Хост `healthcheck.railway.app` должен быть разрешён. Railway healthcheck служит условием готовности нового deployment, а не непрерывным мониторингом уже работающего приложения. Проверять состояние и ошибки после релиза отдельно. Источник: [Railway healthchecks](https://docs.railway.com/deployments/healthchecks).

После первой успешной миграции создать общую учётную запись явно. Открыть SSH-сессию именно web-сервиса в нужном окружении (команду подключения взять из Railway), затем выполнить:

```sh
python manage.py check --deploy
python manage.py createsuperuser
```

Пароль вводится интерактивно; не передавать его аргументом командной строки или в переписке. Проект не открывает Django admin; команда используется для создания первого пользователя, не включает дополнительные продуктовые роли. Для смены пароля: `python manage.py changepassword ИМЯ_ПОЛЬЗОВАТЕЛЯ`. Команда `railway ssh` работает внутри выбранного контейнера, в отличие от локального запуска с подставленными переменными: [Railway SSH](https://docs.railway.com/cli/ssh).

## Миграции и обновление версии

Перед обновлением рабочей версии сохранить JSON-копию и полный `pg_dump`, проверить пробное восстановление на отдельной БД, записать текущие версию/commit, digest образа и список миграций. Если приложение ещё пустое, зафиксировать это вместо копии пользовательских данных. Не обновлять PostgreSQL major одновременно с выпуском приложения.

`scripts/predeploy.py` сначала получает отдельный PostgreSQL advisory lock; конкурирующий релиз завершается ошибкой до изменений. Все текущие миграции атомарны. Скрипт заранее отказывается применять будущие non-atomic миграции: для них понадобится отдельно рассмотренная процедура обслуживания.

Для текущего набора миграций используются одно соединение и одна транзакция: блокировка `DomainState`, миграции и повышение ревизии данных. На пустой БД singleton создаётся миграцией, после чего блокируется. Ошибка откатывает DDL и данные; закрытие соединения освобождает advisory lock. SQL ожидает блокировку не более 15 секунд, отдельный SQL statement — не более 180 секунд; общий предел predeploy задаётся в Railway. Ревизия повышается даже без новых миграций, поэтому формы, открытые до этого повышения, требуют обновления. Значения секретов и доменных объектов скрипт не печатает.

Старая web-версия может обслуживать пользователей, пока работает predeploy и пока новая версия проходит healthcheck. Добавление таблицы в миграции `0012` совместимо с прежней версией. Это не универсальная гарантия бесшовного обновления: удаления/переименования столбцов и несовместимые изменения команд требуют окна обслуживания либо отдельно спроектированных совместимых переходов. При таких изменениях остановить запись, все старые web-процессы и обслуживание; сделать резервные копии; применить миграции; запустить только новую совместимую версию; проверить и открыть доступ. Формы, выданные старой версией уже после predeploy, сами по себе повышением ревизии не защищены от изменения семантики.

После выпуска проверить вход/выход, CSS и JS, сохранение и повторный расчёт на staging, просмотр существующих рабочих записей, JSON/XLSX-выгрузку, журнал и отсутствие неожиданных миграций. В production не создавать фиктивные блюда для smoke-теста. Убедиться, что обслуживание использует тот же релиз; до обновления его версии новые миграции web должны успешно завершиться.

## Ежедневное обслуживание

Отдельный сервис из того же исходного кода/образа и с теми же переменными БД. До его первого запуска web должен завершить миграции; все действия ниже относятся к уже согласованным правилам корзины и очистке технических записей.

| Настройка | Значение |
|---|---|
| Builder / Dockerfile | Те же, что у web |
| Start Command | `sh scripts/start-production.sh maintenance` |
| Pre-deploy Command | Пусто |
| Healthcheck | Пусто |
| Restart Policy | Never |
| Cron Schedule | `0 2 * * *` — ежедневно в 02:00 UTC, 07:00 Asia/Qyzylorda |
| Replicas | 1 |
| Public Domain / Volume | Не нужны |

Команда последовательно запускает `purge_trash`, `purge_restore_sessions`, `purge_login_attempts`, `clearsessions` и завершается. Ошибка останавливает последовательность с ненулевым кодом; после устранения причины повторный запуск допустим. `purge_trash` окончательно удаляет только блюда с истёкшим 30-дневным сроком, сохраняя события журнала. Бессрочную корзину сырья, заготовок и поставщиков он не очищает. Остальные команды удаляют истёкшие подготовки восстановления, технические записи попыток входа старше 24 часов и просроченные Django-сессии.

Расписание Railway работает в UTC; предыдущий незавершённый запуск мешает следующему. Точность до минуты не гарантируется. Поэтому окончательное удаление блюда происходит при ближайшем успешном запуске после срока, а не ровно на 30-й день. Источник: [Railway cron](https://docs.railway.com/cron-jobs).

Не считать deploy доказательством состоявшейся очистки. После первого выпуска проверить Cron Runs и выполнить один явный запуск обслуживания после резервной копии: через UI либо `railway cron run --service maintenance --environment production` с фактическими именами сервиса и окружения. Это реальная очистка просроченных записей, не тест и не dry-run. Дождаться завершения с кодом 0, затем проверить следующий запуск по расписанию. Если Railway уже запустил команду при создании/обновлении, повтор безопасен; инструкция не зависит от такого платформенного поведения. Команда просмотра запусков: `railway cron list --service maintenance --environment production`. Источник: [Railway cron CLI](https://docs.railway.com/cli/cron).

На время восстановления БД или несовместимого обновления остановить обслуживание и расписание. После завершения проверить версию кода и вернуть расписание. Эти команды не делают резервную копию: автоматический backup не настроен.

## Ручные копии и восстановление

Пользовательский путь — «Копии и экспорт» → скачать JSON и сохранить файл отдельно от контейнера. JSON содержит доменные данные, точные значения, историю и состояния корзины; не содержит пароли, пользователей, секреты и сессии. XLSX — отчёт, из него восстановление не выполняется. Ограничения JSON: 25 МиБ, 50 000 записей, глубина 32. Если проверка экспорта отклоняет превышение лимита, не сокращать журнал вручную: сохранить полный dump и отдельно спланировать расширение переноса.

Проверка восстановления JSON: загрузить в отдельное тестовое окружение, сверить состав, пройти предусмотренное подтверждение скачанной предимпортной копии, затем проверить количества записей, точные исходные значения, цены и порядок их применений, журнал, корзину и расчёт контрольных блюд. В рабочем окружении JSON полностью заменяет доменные данные и журнал, поэтому перед подтверждением сохранить предложенную свежую копию. Новое поколение данных отклоняет старые формы. Учётная запись сохраняется; срок корзины блюд восстанавливается из остатка в JSON. Полное поведение описано в разделе резервирования README.

Перед миграциями нужен также PostgreSQL dump, содержащий схему и технические таблицы. Использовать клиент PostgreSQL 17, защищённый файл параметров подключения (`PGSERVICE`/`PGPASSFILE`) и каталог копий вне контейнера. Не записывать пароль в команду. Ниже `tseh-prod` и `tseh-restore-check` — заранее настроенные локальные имена подключений, второе обязано вести к отдельной пустой БД:

```sh
pg_dump --dbname=service=tseh-prod --format=custom --file=tseh-before-release.dump
pg_restore --dbname=service=tseh-restore-check --no-owner --no-privileges --exit-on-error --single-transaction tseh-before-release.dump
```

`pg_dump` делает согласованную копию одной БД, но не сохраняет глобальные роли PostgreSQL; настройки доступа и секреты восстанавливаются отдельно. Dump включает хеши паролей и сессии, поэтому доступ к нему ограничивается. Один `pg_restore --list` не заменяет реального пробного восстановления. Источники: [PostgreSQL 17 pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html), [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).

Для восстановления полного dump остановить web/writers и обслуживание, сохранить аварийную копию текущей БД, восстановить выбранный dump в новую отдельную БД и проверить её совместимым образом приложения. Не применять `--clean` к единственной рабочей БД как пробную операцию. Сравнить данные, вход, расчёты и историю, затем переключить `DATABASE_URL` web и обслуживания на проверенную БД. Учесть и согласовать потерю изменений, выполненных после даты копии.

Полный dump возвращает также прежние ревизии, квитанции команд и сессии. До открытия восстановленного окружения нужно создать новое поколение данных и убрать старые технические подтверждения/входы. В `python manage.py shell` **в восстановленной БД, при остановленных writers** выполнить:

```python
import uuid
from django.db import transaction
from django.contrib.sessions.models import Session
from tseh.models import DomainState, Operation, RestoreSession

with transaction.atomic():
    state = DomainState.objects.select_for_update().get(pk=1)
    state.epoch = uuid.uuid4()
    state.revision += 1
    state.save(update_fields=["epoch", "revision"])
    Operation.objects.all().delete()
    RestoreSession.objects.all().delete()
    Session.objects.all().delete()
```

Эта операция не меняет рецептуры и журнал; пользователи войдут заново, старые формы и отложенные подтверждения применять нельзя. JSON-восстановление уже делает смену поколения своим штатным путём; вручную повторять этот шаг после JSON не требуется.

## Откат и наблюдение

Откат контейнера в Railway не откатывает PostgreSQL. Прежде чем вернуть старый образ, проверить его совместимость с текущей схемой и записанными новой версией данными. Для текущего аддитивного изменения отдельный откат БД обычно не нужен. Для несовместимых изменений выбирать отдельно проверенную обратную миграцию либо восстановление полной копии по процедуре выше; не запускать произвольный `migrate` назад на рабочей БД.

Если predeploy упал, его транзакционные изменения отменены; предыдущая web-версия может продолжать работу. Сначала найти причину в release-логах. Если миграции прошли, а новый web не прошёл healthcheck, БД уже обновлена: проверить совместимость старой версии, настройки host/PORT/HTTPS и доступ к БД, прежде чем повторять релиз.

Gunicorn пишет в stdout/stderr; access-log содержит HTTP-метод, путь, статус и длительность, без query string, cookies и тела запроса. Не включать DEBUG в production ради диагностики. Проверять ошибки 5xx, неуспешный login throttling, память/соединения, успешный ежедневный cron и актуальность отдельно сохранённых копий. Healthcheck Railway не заменяет эту проверку; автоматические внешние уведомления не подключены.

## Что уже проверено и что остаётся

Автоматически проверены секретонезависимый `collectstatic` без подключения к БД, POSIX launcher через Git shell, валидация параметров, порядок четырёх maintenance-команд и прекращение при ошибке. На отдельной PostgreSQL test-БД проверены первый релиз с нулевой схемы, отсутствие демо/пользователей, сохранность данных при повторном релизе, отказ старой формы, конкурирующий release-lock и откат DDL/данных при ошибке. В GitHub Actions дополнительно пройден настоящий Linux Docker/Gunicorn: UID 10001, нестандартный PORT, чистая PostgreSQL 17, predeploy, WhiteNoise, maintenance, secure headers/cookie и контролируемый 503 при отказе БД. Заголовки прокси в этом тесте имитируются; Railway edge он не проверяет.

До допуска рабочих данных остаётся после разрешения создать staging Railway и проверить реальный HTTPS ingress, заголовки, static, health, cron и восстановление. Полученные digest, commit и результаты пользовательской приёмки сохранить в записи выпуска. GitHub CI не публикует образ в registry и не развёртывает Railway.
