# Роли и завершение сеансов — 09.11.2026

Версия кода 0.9.0. Реализация проходит проверку перед выпуском. Этот документ уточняет доступ сотрудников после версии 0.8.0 и решения в staff-access.md.

## Согласованные роли

| Возможность | Владелец | Администратор | Сотрудник |
| --- | --- | --- | --- |
| Рабочие разделы, калькуляции, цены, закупки, журнал | Все права | Все права автоматически | Назначенные разрешения |
| Общие пороги зон | Да | Да | Нет |
| Создание обычных сотрудников, логины, пароли, права, отключение | Да | Да | Нет |
| Назначение, изменение и отключение администраторов | Да | Нет | Нет |
| Полные JSON/XLSX и восстановление | Да | Нет | Нет |
| Завершение сеансов обычных сотрудников | Да | Да | Нет |
| Завершение сеансов администратора | Да | Нет | Нет |
| Завершение всех собственных сеансов владельца | Да | Нет | Нет |

Управление аккаунтами открывается из «Сотрудники». Владелец tseh видит администраторов и сотрудников; администратор — только обычных сотрудников. Ни роль, ни скрытые поля формы не позволяют администратору изменить себя, другого администратора или владельца. Передача владения в этот объём не входит. Создание первого владельца в новой базе остаётся интерактивной командой create_owner.

Роль администратора автоматически выдаёт рабочие права; отдельный список разрешений в его профиле пуст. При понижении до сотрудника сохраняются только явно назначенные в форме права. Автоматический полный доступ администратора не переносится в обычный аккаунт. Изменение роли завершает его существующие входы.

## Завершение сеансов

Действие «Завершить сеансы» находится у активного управляемого аккаунта и имеет отдельный экран подтверждения. Оно завершает все текущие входы этого аккаунта, не меняя пароль, роль, рабочие разрешения и состояние активности. Сотрудник может войти снова с прежним паролем. Для запрета новых входов используется отключение аккаунта.

У владельца есть отдельное действие «Завершить мои сеансы». Подтверждение прямо сообщает, что текущий браузер тоже выйдет из аккаунта. После выполнения открывается страница входа. Остальные аккаунты и их сеансы не затрагиваются.

В истории доступа сохраняются исполнитель, целевой аккаунт, действие и число завершённых сеансов. Пароли, хеши и идентификаторы сеансов в неё не записываются. Администратору не показывается история владельца и административных аккаунтов, в том числе административный период после понижения роли.

## Серверная защита и миграция

Права проверяются сервером заново, включая прямые запросы и ранее открытые подтверждения. Подписанное подтверждение связано с действием, исполнителем и его версией доступа, целевым аккаунтом и его версией; срок действия — один час. Завершение сеансов увеличивает версию доступа, поэтому прежнее подтверждение не становится действительным после повторного входа.

Изменения используют общий порядок блокировок: владельцы, исполнитель, целевой профиль, целевой пользователь. Повторная проверка сеанса после ожидания блокировки сохраняет защиту от продолжения старого POST после отзыва доступа. Подтверждение завершения собственных сеансов очищает текущую авторизацию до ответа, чтобы обработчик сессии не пересохранил удалённый вход.

Миграция 0015 добавляет признак администратора с ложным значением по умолчанию и запрещает одновременные признаки владельца и администратора. Существующие владельцы, обычные сотрудники, их пароли и разрешения сохраняются. Расширяется журнал доступа для действия reset_sessions. Схема совместима с предыдущим кодом на время замены web-процесса. Пользовательские бизнес-копии по-прежнему не переносят аккаунты, роли, сеансы и историю управления доступом.

## Проверки

Целевой набор: 255 тестов прав, сотрудников, ролей и сеансов прошли. Полный набор — 793 Python-теста; пять существующих JavaScript-наборов тоже прошли. Проверены подделка роли, прямые GET/POST, CSRF, повтор и подмена подтверждения, повышение и понижение роли, устаревший доступ, завершение сеансов владельца, сохранение пароля и атомарность операции при ошибке журнала. Независимый рецензент проверил серверные границы и подготовил отдельные HTTP-тесты; другой разработчик проверил модель ролей, миграцию и маршруты.

В браузере на изолированной QA-базе пройдены повышение и понижение роли, автоматические права администратора, запрет управления другими администраторами и владельцем, завершение двух сеансов сотрудника и повторный вход прежним паролем. Владелец завершил собственные сеансы через клавиатуру и вошёл повторно. Проверены экраны 390/1440 px; координатор отдельно просмотрел снимки. Внешние аккаунты при этих проверках не менялись.

Свежие копии обоих окружений восстановлены в отдельных временных базах на соответствующих серверах. Таблицы и последовательности совпали; 103 SQL-ограничения совпали точно, для 11 эквивалентных записей массивных приведений выполнены 94 проверки значений. Временные базы удалены; проверенные копии сохранены в закрытых каталогах существующих PostgreSQL-томов. Это предрелизные копии, а не новая система автоматического внешнего резервирования.

Пользовательская приёмка: владелец создаёт администратора; администратор создаёт сотрудника и назначает ему права, но не может назначить администратора. Затем завершает входы сотрудника: прежний браузер требует входа, прежний пароль по-прежнему подходит. Владелец проверяет отдельное завершение своих сеансов и повторный вход.
